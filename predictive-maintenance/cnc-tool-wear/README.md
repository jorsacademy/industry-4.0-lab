# CNC Tool Wear & Process Health Monitoring

An end-to-end Industry 4.0 condition-monitoring project built on multi-channel CNC controller telemetry. The project models tool condition from the electrical and motion signals generated by the X, Y and Z servo axes and the spindle, while preserving the physical experiment boundaries during validation.

## Why this belongs in Industry 4.0

The data is not a generic tabular classification exercise. It represents a cyber-physical machining process sampled every 100 ms (10 Hz), with controller and motor measurements including:

- actual and commanded position, velocity and acceleration;
- servo and spindle current feedback;
- DC-bus voltage, output current, output voltage and output power;
- spindle inertia and feed-rate information;
- CNC program/sequence information;
- the active machining-process stage.

The repository contains 18 complete machining experiments. Each experiment has a run-level tool-condition label and process outcome metadata. This makes the project suitable for predictive maintenance, process monitoring and edge/IIoT-style inference.

## Primary task

Predict whether the cutting tool is `worn` or `unworn` from time-series machine telemetry.

Secondary targets supported by the same pipeline are:

- whether machining completed successfully;
- whether a completed part passed visual inspection.

The default model is deliberately classical rather than unnecessarily deep. With only 18 independently labelled machining runs, leakage control and physically meaningful feature engineering matter more than model size.

`train.csv` stores run-level labels and process settings. Each `experiment_XX.csv` file contains the 10 Hz controller time series for one complete machining run.

The compact raw dataset is versioned with the project so the analysis is directly reproducible. The data files are distributed under CC0/public-domain terms.

## What was improved

### 1. Group-safe validation

A random row split is invalid here because every row from the same experiment shares the same run-level label. Random splitting would allow nearly identical samples from one physical run to appear in both train and test sets.

This project uses stratified grouped cross-validation where the **experiment number is the group**. An experiment can appear in either training or validation, never both.

### 2. Window-level signal engineering

The raw 10 Hz stream is converted into overlapping time windows. Features include robust time-domain statistics from motion and electrical channels plus tracking-error features derived from actual-versus-commanded signals.

### 3. Known acquisition-artifact handling

Controller values documented as suspicious acquisition states are flagged and can be excluded before window construction. The cleaning decision is explicit in `config.yaml` rather than hidden inside a notebook.

### 4. Run-level model selection

Models predict individual windows, but model selection is based primarily on probabilities aggregated back to the physical experiment. This prevents a long run from dominating evaluation simply because it contains more rows.

### 5. Online inference path

The same feature function used for training is reused for replay/streaming inference. The project can therefore emit a rolling tool-wear probability from the latest sensor window.

## Setup

```bash
cd predictive-maintenance/cnc-tool-wear
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Windows:

```bash
.venv\Scripts\activate
pip install -r requirements.txt
```

## Validate the raw data

```bash
python scripts/validate_data.py
```

The validator checks the expected 18 experiments, metadata labels, signal-column count and basic schema consistency.

## Train and evaluate

```bash
python -m src.train --config config.yaml
```

The training command:

1. loads all 18 experiments;
2. applies the configured data-quality rules;
3. creates overlapping sensor windows;
4. extracts time-domain and controller-tracking features;
5. compares leakage-safe model candidates with grouped cross-validation;
6. aggregates out-of-fold probabilities to the experiment level;
7. writes metrics and predictions to `reports/`;
8. fits the selected model on all available runs and saves it to `artifacts/`.

Generated report files include:

```text
reports/cv_metrics.json
reports/oof_run_predictions.csv
reports/oof_window_predictions.csv
reports/feature_importance.csv
```

## Score one complete experiment

```bash
python -m src.infer data/raw/experiment_18.csv --config config.yaml
```

The output includes the number of valid windows, mean wear probability, median wear probability and the binary operating decision.

## Replay as an online sensor stream

```bash
python -m src.streaming data/raw/experiment_18.csv --config config.yaml --emit-every 10
```

The replay accumulates samples and, once a full window is available, emits a rolling wear probability every 10 samples. At 10 Hz that corresponds to a new health estimate every second.

## Evaluation notes

Because there are only 18 independently labelled runs, apparently high row-level accuracy can be misleading. The most important outputs are the out-of-fold **run-level** probabilities and metrics. Any future extension should keep the experiment/machine/batch boundary intact when estimating generalization performance.

For production deployment, the next step would be to validate on different tools, materials, machines and operating regimes, then calibrate the alert threshold against the economic cost of missed wear versus premature tool replacement.
